\begin{abstract}
This paper studies the 0/1 Knapsack Problem as a canonical NP-Hard optimization problem and evaluates exact and heuristic algorithms under increasing instance sizes. The main algorithmic comparison uses repeated synthetic knapsack instances with $N \in \{100,500,1000,5000,10000\}$ and measures runtime, timeout behavior, objective value, and accuracy gap from the dynamic-programming optimum when that optimum is computationally feasible. Exact dynamic programming gives the optimum for manageable instances but becomes impractical as the $nC$ state space grows, while density-aware greedy and simulated annealing remain efficient with very small gaps on the tested solvable sizes. The second experimental part applies the same budgeted-selection view to TokenPack, an LLM context-packing pipeline where document chunks are items, token counts are weights, and query-conditioned salience is value. The LLM experiments are presented as an application case study, not as a statistically powered retrieval benchmark: they show that knapsack is a useful abstraction for budgeted context selection, but they do not support a claim that knapsack-based selection universally dominates simpler budget-aware retrieval. The strongest practical result is selection-first: on an exploratory 83-case LongBench v2 pilot using Qwen/Qwen2.5-14B-Instruct, TokenPack hybrid-greedy answers 37/83 cases correctly at about 50\% source-token saving, compared with 32/83 for full-context prompting and 34/83 for production-RAG-50. This is a descriptive 15.6\% relative accuracy gain over full context and 8.8\% over production-RAG-50, while the TokenPack-then-LongLLMLingua cascade preserves the same 37/83 correctness at 74.6\% context saving.
\end{abstract}

\section{Introduction}
NP-Hard problems such as the Traveling Salesman Problem, Warehouse Location Problem, and Knapsack Problem are commonly used in algorithm analysis to compare exact and heuristic algorithms. This study focuses on the 0/1 Knapsack Problem. The primary objective is to analyze how dynamic programming, greedy heuristics, randomized feasible selection, and simulated annealing behave as the number of items and the capacity-driven state space grow.

To make the optimization problem concrete beyond synthetic item lists, the paper also uses a modern application scenario: context window selection for large language models (LLMs). When a long document is divided into candidate chunks, only a subset can be placed into the limited token budget of an LLM. This selection task naturally follows a knapsack structure. TokenPack models the context window as a capacity, text chunks as items, token counts as weights, and query relevance scores as values.

The central research question is therefore two-level. First, for the classical 0/1 Knapsack Problem, when does exact DP become too expensive and how close do heuristics stay to the optimum? Second, in the LLM application case study, does the knapsack abstraction help explain the trade-off between relevance value and token cost? This framing keeps the algorithm analysis separate from the application claim: the paper evaluates knapsack solvers rigorously, then tests whether the same abstraction is useful for retrieval-time context packing.

The contribution of this work is fourfold. First, it implements and compares exact DP, greedy, random feasible, and simulated annealing algorithms on repeated 0/1 knapsack instances. Second, it reports runtime, timeout rate, and accuracy gap across increasing item counts, including the point where DP becomes impractical. Third, it presents a direct mapping from LLM context selection to knapsack as an application case study. Fourth, it evaluates chunking, scoring, selection, and compression choices on evidence-oriented retrieval and long-context generation benchmarks, showing where the knapsack abstraction is helpful and where simpler budget-aware heuristics remain stronger.

\section{Literature Review}
The Knapsack Problem is one of the fundamental NP-Hard problems in combinatorial optimization \cite{karp1972reducibility,martello1990knapsack}. Many extensions and solution strategies have been studied, including multidimensional, multiobjective, and multiple-choice variants \cite{cacchiani2022recent,lust2010multiobjective,szkaliczki2025mckp}. Metaheuristic optimization methods such as NSGA-II are also frequently used for combinatorial optimization when exact methods are too expensive \cite{verma2021nsga}.

Retrieval-Augmented Generation (RAG) provides external knowledge to LLMs by retrieving relevant document chunks \cite{lewis2020rag}. However, simple top-k retrieval does not directly optimize token budget usage. Long-context methods such as MemGPT, Parallel Context Windows, LongRoPE, PoSE, and positional interpolation show that context length is a major practical limitation in LLM systems \cite{packer2023memgpt,ratner2023pcw,ding2024longrope,zhu2023pose,chen2023positional}. Recent evaluations also compare long-context models and RAG, and show that effective context length and computational cost still matter even when nominal context windows grow \cite{xu2023retrieval,li2024longcontextrag,paulsen2025effective,ahmed2025optimization}.

Chunking and embedding quality are also central to retrieval. Late Chunking, S2 Chunking, Landmark Embedding, and document chunking studies demonstrate that segmentation and representation choices affect downstream retrieval quality \cite{gunther2024latechunking,verma2025s2chunking,luo2024landmark,luo2024bge,documentchunking2026}. Context pruning and query-aware sparsity methods such as AttentionRAG, Quest, SnapKV, WindowKV, and BudgetMem further support the idea that not every token should be placed into the model context \cite{attentionrag2025,tang2024quest,li2024snapkv,zuo2025windowkv,budgetmem2025}. Prompt-compression methods such as LLMLingua, LongLLMLingua, and LLMLingua-2 attack the same budget problem from a different angle: instead of selecting chunks before prompting, they compress the prompt tokens after context construction \cite{jiang2023llmlingua,jiang2024longllmlingua,pan2024llmlingua2}. BudgetMem is especially relevant because it keeps selection at the chunk level, uses BM25 retrieval after ingestion-time filtering, and scores chunks with interpretable signals such as TF-IDF, position bias, entity density, numerical density, and discourse markers. These neighboring lines of work motivate a broader TokenPack question: the optimizer should be tested not only with different solvers, but also against compression-first alternatives that operate at a different stage of the pipeline.

Knapsack-style formulations have also appeared in summarization and recent LLM optimization work. Tree knapsack summarization and budget-aware summarization explicitly connect content selection with budget constraints \cite{hirao2013treeknapsack,pilault2022factorizing}. Recent LLM-oriented work uses knapsack-like ideas for NP-Hard problem evaluation, exploration budget allocation, and speculative decoding \cite{duchnowski2025knapsack,li2025knapsackrl,cha2026knapspec}. TokenPack follows this direction but focuses specifically on retrieval-time context packing.

\section{Problem Formulation}
The core optimization problem is the standard 0/1 Knapsack Problem. There are $n$ items, each item $i$ has a nonnegative value $v_i$ and a positive weight $w_i$, and the knapsack has capacity $C$. The goal is to select a subset with maximum total value while keeping total weight within capacity.

In the LLM context-packing case study, a query $q$ and a document define the item set. The document is split into $n$ chunks. Each chunk $i$ has value $v_i$ and weight $w_i$. In the default TokenPack scoring setting, $w_i$ is the chunk token count and $v_i$ is the production \textit{evidence-hybrid} score:

\begin{equation}
v_i = 0.35c_i + 0.25b_i + 0.20q_i + 0.15s_i + 0.05h_i
\end{equation}

where $c_i$ is normalized embedding cosine similarity, $b_i$ is normalized BM25 lexical relevance, $q_i$ is explicit query-term coverage, $s_i$ is a structural prior from source metadata, and $h_i$ is adjacent-chunk coherence. These coefficients are hand-set rather than learned: they intentionally combine semantic similarity, lexical matching, evidence coverage, and structural cues. Their relative weights were chosen by engineering judgment and ablation feedback, not by a systematic calibration procedure. They should therefore be read as a transparent evidence-selection heuristic, not as a tuned optimum. The effective LLM context budget is denoted by $C$.

Historical ablations also test cosine-only, hybrid, and knapsack-aware scoring profiles. These profiles are kept in an experimental module to test score alignment, not to claim that their coefficients are theoretically optimal; no hyperparameter sensitivity sweep is claimed in this version. The revised artifact uses \texttt{sentence-transformers/all-MiniLM-L6-v2} as the default embedding model \cite{reimers2019sentencebert,sentenceTransformersMiniLM}; deterministic hash embeddings are no longer used for paper-grade runs.

The optimization problem is:

\begin{equation}
\max \sum_{i=1}^{n} v_i x_i
\end{equation}

\begin{equation}
\sum_{i=1}^{n} w_i x_i \leq C,\quad x_i \in \{0,1\}
\end{equation}

Here, $x_i=1$ means that item or chunk $i$ is selected. In the synthetic experiments, $v_i$ and $w_i$ are generated numerical item attributes. In the LLM case study, the objective maximizes total estimated semantic utility while preserving the hard token budget. This formulation is more informative than fixed top-k retrieval when chunk lengths are unequal, because top-k ignores item weight.

\section{Method}
The TokenPack pipeline has four main stages:

\begin{enumerate}
  \item The long document is split into chunks using the default structure-aware chunker, which preserves structural boundaries and can split within a section when adjacent block embeddings indicate semantic drift.
  \item Each chunk and query is embedded into a vector space.
  \item Chunk value is computed using either cosine similarity or the hybrid salience score, and chunk weight is computed using token count.
  \item Selection is performed with top-k, budget-top-k, MMR, greedy heuristics, or 0/1 knapsack dynamic programming.
\end{enumerate}

\subsection{Semantic Chunking}
Chunking is the stage that converts an unstructured long document into knapsack items. This is important because the optimization algorithm can only choose among the chunks that the preprocessing stage creates. If chunk boundaries are poor, even an optimal knapsack solver may select incomplete or semantically broken evidence.

TokenPack uses \textbf{structure-aware semantic chunking} as the default. The document is first split into structural blocks such as paragraphs, PDF text blocks, sections, and code symbols. Consecutive document blocks are grouped until the chunk reaches a target token range, but the chunker preserves file boundaries, content-type changes, section hints, and function/class boundaries when source code metadata is available. Each chunk keeps metadata such as source path, page number when available, block order, character offsets, and line spans for code. This metadata is important because selected chunks are later restored to their original document order before being sent to the LLM.

Within a structurally compatible run of document blocks, the default chunker also uses a semantic drift check. For two adjacent blocks $b_i$ and $b_{i+1}$, TokenPack computes:

\begin{equation}
s_i = \cos(E(b_i), E(b_{i+1}))
\end{equation}

where $E(\cdot)$ is the embedding function. If $s_i$ falls below a threshold and the current chunk has reached a minimum useful size, the algorithm treats this point as a topic shift and starts a new chunk. Structural boundaries take precedence over semantic boundaries: semantic drift is used to refine otherwise compatible document blocks, not to merge across sections or split code symbols arbitrarily. A maximum token limit is still enforced, so chunking cannot create chunks that violate the later token-budget assumptions.

Paragraph-only and standalone semantic-threshold chunkers remain as ablation baselines. The purpose of chunking is not to solve the optimization problem by itself; it improves the quality of the item set given to knapsack. The output item must contain three values needed by the optimizer: text content, token weight, and source-order metadata.

\subsection{Compared Algorithms}
\textbf{Dynamic Programming (DP).} DP computes the optimal subset under the token capacity. The implementation uses a one-dimensional value table for the objective and a reconstruction table for selected weight. Its time complexity is $O(nC)$.

\textbf{Greedy by Value.} This heuristic sorts chunks by value and inserts each chunk if it fits. It is fast, but it may choose large chunks that block better combinations.

\textbf{Greedy by Value Density.} This heuristic sorts chunks by $v_i/w_i$. It is usually stronger than value-only greedy because it accounts for token efficiency, but it is still not guaranteed to find the optimal 0/1 solution.

\textbf{Greedy by Lightest Weight.} This baseline chooses short chunks first. It tests whether token minimization alone is enough. In practice, it ignores semantic value and therefore may select weak evidence.

\textbf{Random Feasible.} This baseline shuffles chunks and inserts feasible items. It gives a lower-bound style comparison for non-optimized selection.

\textbf{Simulated Annealing (SA).} SA starts from a density-greedy feasible solution and then explores neighboring subsets by adding or removing one item at a time. It uses temperature $\max(1,n/2)$, $\min(25000,\max(2000,12n))$ iterations, multiplicative cooling by 0.9995, and a 1.02 deterministic reheating every 250 steps. This provides a metaheuristic baseline that is more exploratory than simple greedy selection.

\textbf{Document-prefix and Full-document Baselines.} These two baselines represent the system without TokenPack-style optimization. Document-prefix inserts chunks in the original PDF order until the budget is full. Full-document tries to insert the entire source document. These baselines are useful because they show what happens when semantic value and token cost are not optimized jointly.

\textbf{Production-RAG, Top-k, Budget-top-k, and MMR.} The production-RAG baseline represents a common vector-retrieval RAG system: it ranks chunks only by dense embedding cosine similarity to the query, then inserts the highest-similarity chunks until the token budget is full. It does not rewrite, summarize, or compress chunk text; it reduces context length only by selecting fewer chunks. A label such as \texttt{production-rag-50} means that this similarity-ranked retrieval baseline receives a source-relative token budget of about 50\% of the original source context. Top-k selects a fixed number of chunks without checking budget. Budget-top-k uses TokenPack's evidence-hybrid value score rather than raw dense similarity, then adds the same budget-feasibility check. MMR additionally penalizes redundancy between selected chunks. The \texttt{knapsack-redundancy} strategy keeps MMR as a separate algorithm, but applies a redundancy penalty to chunk values before the knapsack solver runs. This is a practical linear approximation rather than a full quadratic knapsack formulation.

These algorithms were not only described theoretically; they were executed on the same generated instances so that their differences can be measured statistically. Table \ref{tab:algorithm-comparison} reports a paired comparison for $N=1000$ over 100 runs. The word ``paired'' means that every algorithm receives the same item values, weights, and capacity for each repetition. Therefore, the measured gap is caused by the algorithmic strategy rather than by different random inputs. In the tables, shaded rows mark the TokenPack-relevant exact knapsack baseline and its practical density-based heuristic.

\subsection{Why Knapsack is Appropriate}
Knapsack is appropriate for this study because it is a canonical NP-Hard problem with a clear exact dynamic-programming baseline and several practical heuristic alternatives. This makes it suitable for comparing runtime, scalability, and approximation quality under the same generated instances.

The mapping from context selection to knapsack is also direct. The context window is the capacity, chunks are items, token counts are weights, and query relevance scores are values. This model is more faithful than fixed top-k retrieval because it optimizes estimated information value under an explicit constraint. However, the LLM setting also shows an important limitation: optimizing the additive knapsack objective is only useful if the value function is well aligned with downstream answer quality.

\section{Complexity Analysis}
For $n$ candidate chunks and effective token budget $C$, the DP algorithm has $O(nC)$ time complexity. This is pseudo-polynomial: it is efficient for moderate token budgets but can become expensive when either the number of chunks or the capacity is large. Greedy algorithms require sorting, so their time complexity is $O(n \log n)$ and memory usage is low.

This theoretical expectation leads to a practical hybrid design. Embedding similarity first prunes the candidate pool, then an exact solver or a strong heuristic is applied only to the strongest candidates. This keeps the optimization stage feasible while preserving the main advantage of budget-aware selection.

\section{Experimental Design}
Eight main experiment groups are used, and the LongBench generation group includes one larger-context diagnostic extension. The first repeated synthetic benchmark is the main classical algorithm-analysis experiment. The remaining experiments use LLM context selection as an application case study for the same budgeted-selection abstraction.

\textbf{Repeated synthetic knapsack benchmark.} Random instances are generated for $N \in \{100,500,1000,5000,10000\}$. Each setting is repeated 100 times with different random seeds. DP is treated as the exact baseline when $nC \leq 5{,}000{,}000$ states. For larger instances, DP is marked as timeout to represent the practical point where the exact method becomes too expensive. The reported metrics are mean objective value, mean runtime, standard deviation of runtime, mean accuracy gap from DP optimum, maximum gap, and timeout rate.

\textbf{Chunking ablation benchmark.} A sample of PDFs from the \texttt{resources} directory is converted into sentence-level source blocks and indexed two ways: standalone semantic-threshold chunking and structure-aware semantic chunking. The evidence targets are defined before chunking as source text spans represented by content terms, so the evaluation does not favor either chunker by using chunk IDs from one index. The solver is fixed to knapsack, scoring is fixed to the evidence-hybrid profile, and budgets are set as 1\%, 3\%, and 5\% of source tokens. This isolates the effect of chunk boundaries from the effect of the selection algorithm and the value function.

\textbf{Value-function ablation benchmark.} The same PDF sample and evidence-term targets are also used to compare several scoring profiles, from cosine-only similarity to richer hybrid and evidence-aware variants. In this experiment, chunking is fixed to structure-aware and selection is fixed to knapsack. Therefore, the only changed variable is the value function used by the optimizer.

\textbf{QASPER selector ablation.} To avoid relying only on the small manually reviewed PDF benchmark, TokenPack is also evaluated on QASPER validation examples with evidence annotations \cite{dasigi2021qasper}. The revised selector harness compares production-RAG, budget-top-k, greedy-density, knapsack, and knapsack-redundancy. Chunking is fixed to structure-aware and scoring is fixed to the evidence-hybrid value function for TokenPack selectors, while production-RAG uses raw dense similarity ranking. Budgets are defined as 20\%, 30\%, 40\%, and 50\% of each paper's source tokens.

\textbf{QASPER cost-quality proxy.} The main practical goal is to reduce input-token cost while preserving answer quality. Because no local or cloud LLM is assumed to be available for every run, this experiment measures answerability proxies on QASPER. For each selector and budget, it records selected-token cost, retained gold-answer token coverage, retained evidence coverage, and the rate at which both answer and evidence are preserved. The answer-token-overlap F1 metric is computed between the selected context text and the gold answer string after lowercasing and token matching. It is therefore a retention proxy rather than a model-output quality score, and its absolute values are expected to be low because the retained context is much longer than the short gold answer and some QASPER answers are mildly abstractive. Scores are reported relative to a 100\% high-budget RAG setting using the same chunker, scoring function, and selector.

\textbf{QASPER compression comparison.} Selection and compression solve related but distinct problems, so they are compared directly on the same QASPER questions. The 200-question subset is not sampled randomly: the script streams QASPER validation papers in dataset order and stops after the first 200 questions from papers with parseable blocks and questions. Three pipelines are evaluated: Only TokenPack, Only LLMLingua-2, and TokenPack followed by LLMLingua-2. The metrics are final token saving, evidence recall, complete-evidence rate, answer-token-overlap F1, latency, and per-question win rates.

\textbf{LongBench v2 generation pilot.} To test whether the evidence-retention signal transfers to downstream long-context answering, a separate Modal-based experiment evaluates the eligible LongBench v2 multiple-choice cases \cite{bai2024longbench2}. The generator is Qwen2.5-14B-Instruct \cite{qwen2024qwen25}. Source contexts are filtered to the 8k--24k token range so that full-context prompting remains feasible within the configured 32k model length. The released split used for this pilot contains 503 examples; the script streams examples in dataset order and yields 83 eligible cases after skipping 420 examples above 24k source tokens and none below 8k. Five methods are compared: full context, production-RAG at a 50\% source-token budget, TokenPack hybrid-greedy at the same 50\% budget with score-then-source context ordering, LongLLMLingua at rate 0.50, and TokenPack followed by LongLLMLingua at rate 0.50. Here, the suffix ``50'' denotes a selection budget equal to approximately half of each example's source tokens, not a model-context-window percentage and not a token-level compression rate. The LongLLMLingua baseline is run in context-level filtering mode, with token-level filtering disabled, so it should be interpreted as a practical LongLLMLingua-style context-pruning baseline rather than a full token-level compression study. Accuracy is exact multiple-choice correctness after parsing the model's A/B/C/D answer.

A larger-context diagnostic reuses the same Modal harness on 32k--58k and 64k--112k source-token windows. It compares full context, production-RAG-50, raw-similarity dynamic programming, evidence-hybrid greedy fill, and evidence-hybrid dynamic programming. These runs contain 30 and 8 cases, respectively, so they are reported as scaling diagnostics rather than as primary accuracy claims.

\textbf{Illustrative input-cost estimate.} A final accounting table scales the LongBench v2 context-reduction ratios to a 1M baseline-token scenario using public API pricing assumptions \cite{openaipricing2026}. This estimate is included only to show the economic implication of token reduction; it is not used as evidence for answer quality.

\textbf{Reproducibility.} The implementation is included in the accompanying artifact as the \texttt{tokenpack} Python package, with a source manifest listing modules, tests, Modal commands, and QASPER reproduction scripts. Until a public repository URL is attached, the package claim should be interpreted as artifact-based rather than independently archival.

More aggressive second-stage compression continues to increase savings, but the frontier shows a consistent pattern: the first quality-preserving step is retrieval-time evidence selection, while prompt compression is best interpreted as an optional second-stage cost reducer with a visible recall trade-off.

\section{Discussion}
The experiments support seven observations. First, exact DP is the most reliable method when the instance size is manageable because it gives the optimum. Second, the $O(nC)$ cost becomes a real limitation as the state space grows: in the repeated benchmark, DP is feasible for the smaller settings but is skipped at the larger state counts. Third, density-aware greedy and simulated annealing are strong practical approximations on the tested solvable sizes because they retain most of the objective value at much lower cost. Fourth, value-only greedy can fail badly, even though it sounds intuitive, because it ignores weight. Fifth, the LLM case study shows that budgeted selection and compression should not be conflated: selecting evidence-bearing chunks before prompting is a different operation from pruning prompt tokens after context construction. Sixth, the LongBench v2 pilot offers hypothesis-generating evidence that this selection-first framing can transfer from evidence-retention proxies to downstream answering: TokenPack hybrid-greedy improves pilot accuracy by 15.6\% relative to full-context prompting while saving about half the source tokens, and the selection-then-compression cascade keeps the same 37/83 correctness while pushing the average saving to 74.6\%. Seventh, the larger-context diagnostics show that the same source-relative half-budget regime is operationally feasible beyond the 32k main pilot, although the 64k--112k sample is too small for a stable method ranking.

For LLM context selection, these observations imply that TokenPack should not run DP over every chunk in a huge corpus. Instead, the retrieval system should first create a candidate pool using embeddings, then apply DP or a strong approximation inside that smaller pool. The QASPER selector results also clarify what TokenPack is and is not proving at this stage. The current paper does not show that knapsack is the universally best retrieval rule under evidence recall. Rather, it shows that budgeted selection is the right abstraction, that solver quality and score quality are separable, and that a stronger score model is now the main limiting factor. In fact, the most robust current retrieval-side rule is the simpler evidence-hybrid budget-top-k selector. Therefore, the appropriate claim is not ``knapsack beats retrieval,'' but ``the 0/1 knapsack framework enables exact-vs-heuristic algorithm analysis, and the LLM setting is a realistic budgeted-selection case study.'' The compression and LongBench comparisons refine the claim further: TokenPack does not make the language model itself smarter, but it selects an evidence substrate and can improve the operating point of a downstream compressor. Prompt compression can still be valuable after selection, especially when a system must push to higher savings, yet the QASPER frontier and the LongBench cascade both suggest that selection-first pipelines are a better framing than treating compression as the only budget-control step.

\section{Limitations and Future Work}
The current results are strongest on synthetic knapsack instances, where the optimum and approximation gap are clearly defined. The LLM experiments should be treated as an application case study rather than as proof of universal retrieval dominance. QASPER measures retention proxies rather than final human-judged answer quality, and the LongBench accuracy differences are descriptive rather than statistically significant at this sample size. The larger-context LongBench rows are even more diagnostic: the 32k--58k window has 30 cases and the 64k--112k window has only 8 cases. A further limitation is the production scoring function itself: although the evidence-hybrid formula exposes its component weights, this version does not derive those weights from a held-out calibration set, a learned ranker, or a sensitivity study. Future work should tune or learn these coefficients and report how stable the selector rankings are under reasonable weight changes. The compression comparison focuses on one family of methods, uses LongLLMLingua context-level filtering rather than the full token-level compressor, and reports realized savings but not full per-document rate variance. BudgetMem is discussed as related work, but no direct numerical BudgetMem baseline is included because the study did not have an official implementation or exact reproduction artifact; the artifact includes only a BudgetMem-style feature proxy, which trails evidence-hybrid on QASPER. A larger study should add full LongLLMLingua token-level compression, a true BudgetMem reproduction if code becomes available, KV-compression baselines, more generator models, human review of disagreement cases, and learned or tuned scoring and chunk-size policies.

\section{Conclusion}
This paper evaluates the 0/1 Knapsack Problem through exact and heuristic algorithms and uses LLM context packing as a realistic application of budgeted selection. The algorithm-analysis result is clear: exact DP is optimal but scales with the pseudo-polynomial $O(nC)$ state space, while density-aware greedy and simulated annealing are much faster and stay close to the optimum on the tested solvable instances. The application-side result is intentionally nuanced: hybrid-greedy remains the strongest QASPER evidence-recall baseline under the current scoring function, so the paper does not claim universal knapsack dominance for LLM retrieval. Instead, the LLM experiments show why budgeted selection is useful and why retrieval-time selection and prompt compression are not interchangeable. TokenPack preserves substantially more QASPER evidence than LLMLingua-2 at matched 50\% token savings. The LongBench v2 pilot is best read as descriptive case-study evidence: TokenPack hybrid-greedy improves accuracy by 15.6\% relative to full-context prompting while using about half the context, and the TokenPack-then-LongLLMLingua cascade preserves the same 37/83 correctness while increasing context saving to 74.6\%. Future gains will depend on utility models better aligned with downstream answer quality and on larger generation benchmarks.
